# سبک کد

> فصل ۷ — قواعد · خلاصهٔ انگلیسی در `AGENTS.md` (بخش Conventions)

## اصول
1. **اعتبارسنجی فقط در `packages/shared`.** API هر ورودی را parse می‌کند و وب از همان schemaها
   استفاده می‌کند. هیچ‌وقت قاعدهٔ اعتبارسنجی را در وب یا API تکرار نکنید.
2. **امنیت در API.** هر محدودیتی که در رابط کاربری هست (پنهان کردن دکمه، قفل مشتری، ماژول خاموش)
   باید در API هم با middleware اعمال شود.
3. **دادهٔ سایت فقط از `req.tenant.db`.** هیچ handlerی نباید به دیتابیس سایت دیگری برسد.
4. **سازگاری با گذشته.** سایت‌های قدیمی و سرورهای مشتری باید بدون دخالت کار کنند: پیش‌فرض در schema،
   `withSettingDefaults`، تبدیل نسخهٔ قدیمی هنگام خواندن، و migrationی که روی دادهٔ موجود درست کار کند.
5. **مبلغ و موجودی را از مرورگر قبول نکنید.** روی سرور دوباره حساب کنید.

## نام‌گذاری
| کجا | قاعده |
|---|---|
| ستون‌ها و جدول‌ها | `snake_case` (`created_at`) |
| JSON پاسخ و TypeScript | `camelCase` (`createdAt`)؛ تبدیل در SQL با `AS "createdAt"` |
| مبلغ | پسوند `_minor` / `Minor` |
| فایل‌های API | `modules/<name>/<name>.routes.ts` و `<name>.service.ts` |
| کامپوننت‌ها | `PascalCase.tsx` |
| slugها | حروف کوچک، عدد، خط تیره |

## متن کاربر
- **همهٔ متن‌های رابط کاربری دوزبانه‌اند:** `L('English', 'فارسی')` یا `{ en, fa }`؛ متن‌های مشترک پنل
  در `admin/i18n.ts`.
- **خطاها:** API یک `code` و حدود را می‌فرستد. جملهٔ کاربر در `apps/web/src/lib/errorText.ts` ساخته
  می‌شود. برای خطای جدید یک code روشن مثل `module_disabled` انتخاب کنید و متن فارسی و انگلیسی‌اش
  را اضافه کنید.
- جهت را با کلاس‌های منطقی بنویسید (`ms-`، `me-`، `text-start`)، نه `left` و `right`، تا RTL و LTR
  هر دو درست باشند.

## کامنت‌ها
- انگلیسی و ساده؛ توضیح بدهید **چرا** یا **برای چه**، نه اینکه کد چه می‌کند.
- با تراکم کامنت‌های اطراف هماهنگ باشید. فایل‌های این پروژه بالای هر تابع export‌شده یک `/** … */`
  کوتاه دارند.
- اگر کدی را از روی مستندات خارجی نوشته‌اید و تست واقعی نشده است، همین را در کامنت بنویسید (نمونه:
  درگاه‌های پرداخت).

## دادهٔ نمونه
هر ردیف ساختگی `demo = true` دارد تا با هم حذف شود و در بستهٔ مشتری نرود.

## صفحه‌های داخلی
قابلیت‌های داخلی از طریق slugهای ثابت (`SYSTEM_PAGES`) به‌صورت صفحهٔ builder قابل ویرایش می‌شوند؛
برای هر صفحهٔ داخلی جدید همین الگو را دنبال کنید ([صفحات داخلی](../04-features/system-pages.md)).

## پیش از اینکه بگویید کار تمام است
1. `npm run typecheck` بدون خطا.
2. `npm test` سبز. هر شکست جدید باید توضیح داده شود.
3. رفتار جدید API یک تست در `apps/api/test/` دارد.
4. کانتینرها rebuild شده‌اند و تغییر در http://admin.localhost بررسی شده است.
5. مستندات به‌روز شده است ([قواعد مستندات](docs.md)).
